React apps tend to slow down in predictable ways: long lists that render every item at once, images loading before they're needed, components re-rendering when nothing relevant changed, or expensive calculations running on every keystroke.

The good news is that React (and the wider ecosystem) gives us a solid toolkit for each of these problems. This post walks through the most commonly used techniques, how they work, and — just as important — when they're actually worth reaching for.

<Callout type="info" title="Optimize with intent">
  Every technique here adds some complexity. Use them to fix a real performance
  problem you've noticed or measured, not as a checklist to apply to every
  component.
</Callout>

## List virtualization (windowing)

When you render a list with thousands of items, React creates a DOM node for every single one — even the ones the user can't see. This wastes memory and slows down both the initial render and any updates.

List virtualization (or "windowing") solves this by only rendering the items currently visible in the viewport, plus a small buffer. As the user scrolls, items that move off-screen are removed from the DOM and new ones are rendered in their place. The library `react-virtualized` (and its successor `react-window`) handles all of this measurement and recycling for you.

```jsx
// filename: VirtualizedList.jsx
import { List } from 'react-virtualized';

function VirtualizedList({ items }) {
  const rowRenderer = ({ index, key, style }) => (
    <div key={key} style={style}>
      {items[index]}
    </div>
  );

  return (
    <List
      width={400}
      height={400}
      rowCount={items.length}
      rowHeight={40}
      rowRenderer={rowRenderer}
    />
  );
}
```

Here, `List` only renders enough rows to fill the 400px-tall container, regardless of whether `items` has 100 entries or 100,000. The `style` prop passed into `rowRenderer` is what positions each row correctly as the user scrolls.

<Callout type="tip" title="When to use it">
  Reach for virtualization when you're rendering long lists or tables — think
  hundreds of rows or more. For short lists (say, under 50 items), the overhead
  isn't worth it.
</Callout>

## Lazy loading images

Loading every image on a page up front — especially on image-heavy pages — can significantly slow down the initial load, even if most of those images are far below the fold and won't be seen for a while.

Lazy loading defers loading an image until it's about to enter the viewport. Until then, a lightweight placeholder is shown instead. The browser's **Intersection Observer API** is the modern way to detect when an element scrolls into view, and libraries like `react-lazyload` wrap this pattern into a ready-made component.

```jsx
// filename: LazyImage.jsx
import { useEffect, useRef, useState } from 'react';

function LazyImage({ src, alt }) {
  const imgRef = useRef(null);
  const [isVisible, setIsVisible] = useState(false);

  useEffect(() => {
    const observer = new IntersectionObserver(([entry]) => {
      if (entry.isIntersecting) {
        setIsVisible(true);
        observer.disconnect();
      }
    });

    if (imgRef.current) observer.observe(imgRef.current);

    return () => observer.disconnect();
  }, []);

  return (
    <img ref={imgRef} src={isVisible ? src : '/placeholder.png'} alt={alt} />
  );
}
```

The observer watches the `<img>` element and flips `isVisible` to `true` the moment it scrolls into the viewport. Once that happens, we swap the placeholder for the real image source and disconnect the observer, since we don't need to keep watching.

<Callout type="tip" title="Native alternative">
  For simple cases, the browser's built-in `loading="lazy"` attribute on
  `<img>` tags handles this automatically without any JavaScript — worth
  trying before reaching for a library.
</Callout>

## Memoization

Memoization means caching the result of a computation (or a render) so it doesn't have to be redone unless something it depends on actually changes. React provides three main tools for this, and they solve slightly different problems.

**`React.memo()`** wraps a component and tells React to skip re-rendering it if its props haven't changed since the last render. This is useful for components that are expensive to render but don't depend on most of their parent's state.

**`useMemo()`** caches the _result_ of a computation. React only re-runs the calculation when one of the values in the dependency array changes — otherwise it returns the cached value from last time.

**`useCallback()`** is similar to `useMemo`, but instead of caching a computed value, it caches a _function reference_. This matters because every time a component re-renders, any functions defined inside it are recreated as new objects — which would cause a `React.memo`-wrapped child receiving that function as a prop to re-render anyway, defeating the memoization.

```jsx
// filename: Memoization.jsx
import { memo, useMemo, useCallback, useState } from 'react';

const ExpensiveChild = memo(function ExpensiveChild({ onClick, label }) {
  console.log('ExpensiveChild rendered');
  return <button onClick={onClick}>{label}</button>;
});

function Parent({ items }) {
  const [count, setCount] = useState(0);

  // Recomputed only when `items` changes
  const total = useMemo(() => {
    return items.reduce((sum, item) => sum + item.value, 0);
  }, [items]);

  // Same function reference across re-renders
  const handleClick = useCallback(() => {
    setCount((c) => c + 1);
  }, []);

  return (
    <div>
      <p>Total: {total}</p>
      <p>Count: {count}</p>
      <ExpensiveChild onClick={handleClick} label="Increment" />
    </div>
  );
}
```

In this example, clicking the button updates `count` and re-renders `Parent`. Without `useMemo`, the `total` calculation would re-run on every render even though `items` hasn't changed. Without `useCallback`, `handleClick` would be a new function on every render, causing `ExpensiveChild` to re-render despite being wrapped in `memo`.

<Callout type="warning" title="Don't memoize everything">
  Memoization itself has a cost — React has to store and compare cached values.
  Overusing `useMemo` and `useCallback` on cheap computations or components can
  add overhead without any real benefit. Profile first, then apply memoization
  where it actually matters.
</Callout>

## Throttling and debouncing

Both throttling and debouncing limit how often a function runs in response to frequent events — but they do it in different ways and suit different situations.

### Throttling

Throttling ensures a function runs at most once per a fixed interval, no matter how many times the triggering event fires. This is ideal for events that fire continuously and rapidly, like scrolling or window resizing — where you want to react to the event, but not on every single frame.

```jsx
// filename: throttle-example.js
function createThrottledHandler() {
  let throttled = false;

  return () => {
    if (!throttled) {
      // business logic — runs immediately

      throttled = true;

      // wait before allowing the next call
      setTimeout(() => {
        throttled = false;
      }, 2000);
    }
  };
}

window.addEventListener('resize', createThrottledHandler());
```

With this pattern, no matter how many resize events fire in a 2-second window, the business logic only runs once at the start of that window. The next call is only allowed once the timeout clears the `throttled` flag.

### Debouncing

Debouncing takes the opposite approach: instead of running periodically, it waits until the event _stops_ firing for a specified period before running. This is ideal for things like search inputs, where you want to wait until the user has finished typing before making an API call.

```jsx
// filename: SearchInput.jsx
function SearchInput() {
  const [searchTerm, setSearchTerm] = useState('');
  const [debouncedTerm, setDebouncedTerm] = useState('');

  // Wait 1s after the last change to searchTerm before updating debouncedTerm
  useEffect(() => {
    const timer = setTimeout(() => {
      setDebouncedTerm(searchTerm);
    }, 1000);

    return () => {
      clearTimeout(timer); // Cancel previous timeout if searchTerm changes again
    };
  }, [searchTerm]);

  // Runs only once debouncedTerm settles
  useEffect(() => {
    if (debouncedTerm) {
      // fetchData(debouncedTerm);
    }
  }, [debouncedTerm]);

  return (
    <input
      type="text"
      placeholder="Type to search..."
      value={searchTerm}
      onChange={(e) => setSearchTerm(e.target.value)}
    />
  );
}
```

Every keystroke resets the 1-second timer via the cleanup function. Only when the user pauses for a full second does `debouncedTerm` actually update, triggering the search.

<Callout type="tip" title="Quick way to remember the difference">
  Throttling: "run at most once every X seconds, no matter what." Debouncing:
  "run once, X seconds after the last event."
</Callout>

## Code splitting

By default, a React app's JavaScript bundle includes the code for every page and component, even ones the user may never visit. As an app grows, this bundle can become large enough to noticeably slow down the initial page load.

Code splitting breaks the bundle into smaller chunks that are loaded on demand. `React.lazy()` lets you define a component that's only fetched when it's actually rendered, and `Suspense` lets you show a fallback (like a loading spinner) while that chunk is being downloaded.

```jsx
// filename: CodeSplitting.jsx
import { lazy, Suspense } from 'react';

const HeavyChart = lazy(() => import('./HeavyChart'));

function Dashboard() {
  return (
    <Suspense fallback={<p>Loading chart...</p>}>
      <HeavyChart />
    </Suspense>
  );
}
```

The code for `HeavyChart` is split into its own file and only downloaded when `Dashboard` renders it for the first time. Until then, users see the `fallback` content. This is especially effective for route-based splitting, where each page of your app is its own chunk.

## React Fragments

Every component must return a single root element — but wrapping everything in an extra `<div>` just to satisfy this rule adds unnecessary nodes to the DOM. Over many components, these extra wrapper `<div>`s add up and can complicate your CSS layout (especially with flexbox or grid).

`React.Fragment` (or its shorthand, `<>...</>`) lets you group multiple elements without adding any extra node to the DOM at all.

```jsx
// filename: FragmentExample.jsx
// ❌ Adds an unnecessary <div> to the DOM
function SomeComponentBad() {
  return (
    <div>
      <Nav />
      <Hero />
    </div>
  );
}

// ✅ No extra node — Nav and Hero become direct siblings in the DOM
function SomeComponentGood() {
  return (
    <React.Fragment>
      <Nav />
      <Hero />
    </React.Fragment>
  );
}

// Shorthand syntax
function SomeComponentShort() {
  return (
    <>
      <Nav />
      <Hero />
    </>
  );
}
```

This is a small change, but it keeps your DOM tree cleaner and avoids subtle layout issues caused by unintended wrapper elements.

## The `useTransition` hook

By default, when an event handler calls multiple `setState` functions, React batches them into a single update — the component re-renders once, after all the state changes are applied. Usually, this is exactly what you want.

But sometimes one of those updates is expensive. Consider a search input that filters a large dataset on every keystroke:

```jsx
// filename: handleChange.js
const handleChange = (e) => {
  setSearchQuery(e.target.value);
  setFilterData();
  // loop over a million items to filter results
};
```

Both `setSearchQuery` and `setFilterData` are batched together, so the component doesn't re-render until _both_ are done — including the expensive filtering loop. If the user types quickly, each keystroke triggers this slow combined update, and the input itself starts to feel laggy, because even updating the text in the box is blocked by the filtering work.

`useTransition` solves this by letting you mark certain state updates as **low priority**. React will prioritize urgent updates (like updating the input's value) and process the low-priority ones in the background, without blocking the UI.

```jsx
// filename: useTransition-example.jsx
import { useState, useTransition } from 'react';

function SearchableList({ allItems }) {
  const [searchQuery, setSearchQuery] = useState('');
  const [filteredItems, setFilteredItems] = useState(allItems);
  const [isPending, startTransition] = useTransition();

  const handleChange = (e) => {
    const value = e.target.value;
    setSearchQuery(value); // high priority — keeps the input responsive

    startTransition(() => {
      // low priority — runs in the background
      setFilteredItems(allItems.filter((item) => item.includes(value)));
    });
  };

  return (
    <div>
      <input value={searchQuery} onChange={handleChange} />
      {isPending ? (
        <p>Updating results...</p>
      ) : (
        <FilterItems items={filteredItems} />
      )}
    </div>
  );
}
```

Here, `setSearchQuery` runs immediately, so the input field stays responsive as the user types. The expensive filtering, wrapped in `startTransition`, is treated as low priority — React works on it once there's no higher-priority work pending, and `isPending` lets us show a loading state in the meantime.

<Callout type="warning" title="This causes more re-renders, not fewer">
  Without `useTransition`, both updates would be batched into a single
  re-render. With it, the component re-renders once for the high-priority update
  and again when the low-priority update finishes — so use it only when an
  expensive update is actually causing the UI to feel unresponsive.
</Callout>

## Summary

| Technique           | Purpose                                  | When to reach for it                     |
| ------------------- | ---------------------------------------- | ---------------------------------------- |
| List virtualization | Render only visible list items           | Long lists or tables (100s+ rows)        |
| Lazy loading images | Load images on scroll into view          | Image-heavy pages                        |
| `React.memo()`      | Skip child re-renders on unchanged props | Expensive child components               |
| `useMemo()`         | Cache expensive computations             | Heavy calculations tied to specific deps |
| `useCallback()`     | Cache function references                | Passing callbacks to memoized children   |
| Throttling          | Limit call frequency at intervals        | Scroll/resize handlers                   |
| Debouncing          | Delay call until activity stops          | Search inputs, autosave                  |
| Code splitting      | Load code on demand                      | Large bundles, route-based splits        |
| React Fragments     | Avoid extra DOM nodes                    | Grouping sibling elements                |
| `useTransition`     | Prioritize urgent state updates          | Heavy filtering/search UIs               |

<Callout type="info" title="Bottom line">
  These techniques are powerful, but they're solutions to specific problems —
  not defaults. Profile your app, find where the actual bottlenecks are, and
  apply the technique that fits. Premature optimization can make your code
  harder to maintain without delivering any real performance win.
</Callout>
