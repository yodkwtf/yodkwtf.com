Authentication is one of those things that's easy to get _mostly_ working and surprisingly tricky to get _right_. A common pattern in single-page apps is to handle login entirely in the browser using a library like MSAL.js — but as an app grows, especially toward server-side rendering and enterprise requirements, this approach starts to show its limits.

This post walks through migrating from **frontend-owned authentication** to **backend session orchestration** using Azure AD B2C, OAuth 2.0 with PKCE, and JWT cookies — by calling Azure's OAuth endpoints directly with plain HTTP requests, rather than relying on the MSAL SDK.

<Callout type="info" title="Why call the endpoints directly?">
  Azure B2C's OAuth 2.0 flow is just standard HTTP — a few well-defined
  endpoints for authorization, token exchange, and refresh. Calling them
  directly means no SDK dependency, full visibility into every request and
  response, and an implementation that's easy to port to any language or
  framework. The trade-off is that you're responsible for implementing PKCE
  yourself, which this post covers in full.
</Callout>

## Why move auth to the backend?

In a frontend-owned setup, the browser talks directly to Azure B2C, receives tokens, and stores them (often in memory or session storage). The frontend is responsible for attaching tokens to API requests, refreshing them when they expire, and deciding whether the user is logged in.

This works, but it has some downsides:

- **Token exposure**: tokens living in the browser are more exposed to XSS attacks than `httpOnly` cookies.
- **Refresh complexity**: refresh logic has to be duplicated or carefully shared across every page/component that needs it.
- **SSR doesn't fit naturally**: if you're server-rendering pages, the server doesn't know whether the user is authenticated until the frontend tells it — which defeats the purpose of SSR.

Moving auth to the backend flips this around. The backend becomes the **single source of truth** for authentication:

- It owns login, logout, token refresh, and the token lifecycle.
- It protects routes via middleware _before_ anything is rendered.
- The frontend becomes a thin **UI state layer** — it just reflects whether the user is logged in and shows their info, without making any auth decisions itself.

<Callout type="tip" title="Why this fits SSR so well">
  Because authentication is resolved *before* the page is rendered, your
  server-rendered views can simply assume "if you're seeing this page, you're
  authenticated" — no client-side redirects or loading states needed.
</Callout>

## Understanding OAuth 2.0 and PKCE

Before diving into code, it helps to understand the flow we're implementing — especially since we're handling each step's HTTP request ourselves.

**OAuth 2.0 Authorization Code flow** is the standard way for an application to get permission to access resources on a user's behalf, without ever seeing their password. Instead, the user authenticates directly with the identity provider (Azure B2C), which then hands the application a short-lived **authorization code** by redirecting the browser back to a `redirect_uri` with a `code` query parameter. The application then exchanges this code for tokens via a server-to-server request.

**PKCE (Proof Key for Code Exchange)**, pronounced "pixy," is an extension to this flow that protects against intercepted authorization codes. It works like this:

1. Before redirecting the user to Azure B2C, the app generates a random string called the **code verifier**.
2. The app computes a SHA-256 hash of the verifier and base64url-encodes it — this is the **code challenge**.
3. The code challenge is sent to Azure as part of the authorization request.
4. When exchanging the authorization code for tokens later, the app sends the _original_ code verifier.
5. Azure recomputes the hash and checks it matches the code challenge from step 3 — proving the token request is coming from the same client that started the flow.

Even though we're also using a client secret (making this a "confidential client" flow), including PKCE is recommended by Azure and adds a layer of protection against authorization code interception.

## The overall flow

At a high level, here's what happens when a request comes in:

```txt
GET /
  ↓
Auth middleware
  ↓
Validate access token
  ↓
Refresh if expired
  ↓
Allow page to render
```

And here's the login journey itself:

```txt
/login
  ↓
/auth/start (generate PKCE pair, redirect to Azure)
  ↓
Azure B2C
  ↓
/auth/callback (exchange code for tokens)
  ↓
Set JWT cookies
  ↓
redirect /
```

The user clicks "sign in," gets redirected to Azure B2C's hosted login page, authenticates there, and is sent back to our app's callback route with an authorization code. Our backend exchanges that code for tokens via a direct HTTP call to Azure's token endpoint, and stores the resulting tokens as `httpOnly` cookies — meaning they're never accessible to JavaScript running in the browser.

From that point on, every request goes through an auth middleware, which checks the cookies, refreshes the access token if it's expired, and either allows the request through or redirects to `/login`.

<Callout type="info" title="Why httpOnly cookies?">
  Cookies marked `httpOnly` can't be read by client-side JavaScript, which
  significantly reduces the risk of token theft via XSS attacks. The trade-off
  is that your frontend can no longer directly inspect the tokens — but in this
  architecture, it doesn't need to.
</Callout>

## Step 1: Install dependencies

Since we're calling Azure's endpoints with plain HTTP, we only need a couple of small utilities:

```bash
npm install cookie-parser jsonwebtoken
```

And, if you're using TypeScript, their type definitions:

```bash
npm install -D @types/cookie-parser @types/jsonwebtoken
```

We'll use Node's built-in `crypto` module for generating the PKCE values, and the built-in `fetch` (available in modern Node versions) for calling Azure's endpoints — no additional HTTP client library required.

## Step 2: Configure environment variables

Add the following to your `.env` file:

```env
B2C_CLIENT_ID=YOUR_CLIENT_ID
B2C_CLIENT_SECRET=YOUR_CLIENT_SECRET
B2C_TENANT=YOUR_TENANT
B2C_POLICY=YOUR_POLICY
B2C_REDIRECT_URI=http://localhost:3000/auth/callback
B2C_SCOPES=openid profile offline_access
```

A quick rundown of what each value represents:

- **`B2C_CLIENT_ID`** — the application (client) ID registered in your Azure B2C tenant.
- **`B2C_CLIENT_SECRET`** — the secret generated for your app registration, used to prove the backend's identity to Azure.
- **`B2C_TENANT`** — your B2C tenant name (e.g. `contoso` for `contoso.onmicrosoft.com`).
- **`B2C_POLICY`** — the user flow (policy) name you're using, such as `B2C_1_signupsignin`.
- **`B2C_REDIRECT_URI`** — where Azure B2C sends the user back to after they authenticate. This must exactly match what's registered in your app registration.
- **`B2C_SCOPES`** — the permissions your app is requesting.

<Callout type="warning" title="offline_access is required">
  Without the `offline_access` scope, Azure B2C will **not** issue a refresh
  token — only an access token. Since our whole refresh-on-expiry flow depends
  on having a refresh token, this scope is non-negotiable.
</Callout>

From these values, we can construct the two endpoints we'll call directly:

```txt
Authorization endpoint:
https://{tenant}.b2clogin.com/{tenant}.onmicrosoft.com/{policy}/oauth2/v2.0/authorize

Token endpoint:
https://{tenant}.b2clogin.com/{tenant}.onmicrosoft.com/{policy}/oauth2/v2.0/token
```

## Step 3: Load environment variables early

At the very top of your application's entry file, load environment variables before anything else:

```ts
// filename: index.ts
import 'dotenv/config';
```

This has to come before any other imports, because other modules read `process.env` values at the moment they're imported. If `dotenv` hasn't run yet, those values would be `undefined`.

## Step 4: Enable cookie parsing

Import `cookie-parser`:

```ts
// filename: index.ts
import cookieParser from 'cookie-parser';
```

And register it as middleware before defining your routes:

```ts
// filename: index.ts
app.use(cookieParser());
```

`cookie-parser` populates `req.cookies` with parsed cookie values from incoming requests. We'll need this both to read our auth cookies, and — as you'll see in Step 6 — to temporarily store the PKCE code verifier between the start of the flow and the callback.

## Step 5: Set up the auth module structure

Create a folder for everything auth-related, e.g.:

```txt
src/auth/
```

We'll build out four pieces here: a small set of Azure config helpers, PKCE/token helper functions, route handlers, and a middleware.

## Step 6: Create Azure endpoint config and PKCE helpers

Create `src/auth/azure-config.ts` to centralize the endpoint URLs and PKCE generation:

```ts
// filename: src/auth/azure-config.ts
import crypto from 'crypto';

const TENANT = process.env.B2C_TENANT!;
const POLICY = process.env.B2C_POLICY!;

export const AUTHORIZE_ENDPOINT = `https://${TENANT}.b2clogin.com/${TENANT}.onmicrosoft.com/${POLICY}/oauth2/v2.0/authorize`;

export const TOKEN_ENDPOINT = `https://${TENANT}.b2clogin.com/${TENANT}.onmicrosoft.com/${POLICY}/oauth2/v2.0/token`;

// Generates a random, URL-safe code verifier
export function generateCodeVerifier(): string {
  return crypto.randomBytes(32).toString('base64url');
}

// Derives the code challenge from a code verifier using SHA-256
export function generateCodeChallenge(verifier: string): string {
  return crypto.createHash('sha256').update(verifier).digest('base64url');
}
```

A couple of notes on the crypto here:

- **`generateCodeVerifier`** creates 32 random bytes and encodes them as a `base64url` string — `base64url` (rather than regular base64) avoids characters like `+`, `/`, and `=` that aren't safe to use directly in URLs.
- **`generateCodeChallenge`** hashes the verifier with SHA-256 and encodes the result the same way. This is the "S256" challenge method, which is what Azure B2C expects.

## Step 7: Create token helper functions

Next, create the logic for exchanging codes/refresh tokens with Azure, checking expiry, and clearing cookies. Create `src/auth/auth.service.ts`:

```ts
// filename: src/auth/auth.service.ts
import jwt from 'jsonwebtoken';
import { Response } from 'express';
import { TOKEN_ENDPOINT } from './azure-config';

interface JwtPayload {
  exp?: number;
  [key: string]: unknown;
}

interface TokenResponse {
  access_token: string;
  refresh_token?: string;
  id_token?: string;
  expires_in: number;
  token_type: string;
}

export function isExpired(token: string): boolean {
  try {
    const decoded = jwt.decode(token) as JwtPayload | null;

    if (!decoded?.exp) {
      return true;
    }

    return decoded.exp * 1000 < Date.now();
  } catch {
    return true;
  }
}

export function clearAuthCookies(res: Response) {
  res.clearCookie('access_jwt');
  res.clearCookie('refresh_jwt');
}

// Exchange an authorization code for tokens
export async function exchangeCodeForTokens(
  code: string,
  codeVerifier: string,
): Promise<TokenResponse> {
  const params = new URLSearchParams({
    client_id: process.env.B2C_CLIENT_ID!,
    client_secret: process.env.B2C_CLIENT_SECRET!,
    grant_type: 'authorization_code',
    code,
    redirect_uri: process.env.B2C_REDIRECT_URI!,
    scope: process.env.B2C_SCOPES ?? '',
    code_verifier: codeVerifier,
  });

  const response = await fetch(TOKEN_ENDPOINT, {
    method: 'POST',
    headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
    body: params.toString(),
  });

  if (!response.ok) {
    throw new Error(`Token exchange failed: ${await response.text()}`);
  }

  return response.json();
}

// Exchange a refresh token for a new access token
export async function refreshAccessToken(
  refreshToken: string,
): Promise<TokenResponse> {
  const params = new URLSearchParams({
    client_id: process.env.B2C_CLIENT_ID!,
    client_secret: process.env.B2C_CLIENT_SECRET!,
    grant_type: 'refresh_token',
    refresh_token: refreshToken,
    scope: process.env.B2C_SCOPES ?? '',
  });

  const response = await fetch(TOKEN_ENDPOINT, {
    method: 'POST',
    headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
    body: params.toString(),
  });

  if (!response.ok) {
    throw new Error(`Token refresh failed: ${await response.text()}`);
  }

  return response.json();
}
```

A few things worth calling out:

- **`isExpired`** decodes the JWT _without verifying its signature_ (`jwt.decode`, not `jwt.verify`) — we're only reading the `exp` claim to check the timestamp, not validating that the token is genuine. Signature verification of tokens issued by Azure is handled by Azure itself when the token is used; here we just need to know whether it's stale enough to warrant a refresh.
- **`clearAuthCookies`** is a small helper used whenever we need to log a user out or invalidate their session — for example, if a refresh attempt fails.
- **`exchangeCodeForTokens`** and **`refreshAccessToken`** both POST to the same token endpoint, with different `grant_type` values (`authorization_code` vs `refresh_token`). Both calls include the `client_secret`, since this is a confidential client; `exchangeCodeForTokens` additionally sends the `code_verifier`, which Azure checks against the `code_challenge` sent during `/auth/start`.
- The token endpoint returns a JSON body with `access_token`, `refresh_token`, `expires_in`, and other fields — we type this loosely as `TokenResponse` and use what we need.

<Callout type="tip" title="Confidential client + PKCE together">
  Sending both a `client_secret` *and* a `code_verifier` might look redundant —
  and for a pure confidential client, the secret alone is often considered
  sufficient. But Azure B2C accepts and validates PKCE parameters regardless,
  and including them costs little while adding defense in depth.
</Callout>

## Step 8: Create the auth routes

The routes handle the actual HTTP endpoints: the login page, the route that kicks off the Azure B2C flow (generating the PKCE pair), the callback Azure redirects back to, and logout.

Create `src/auth/auth.routes.ts`:

```ts
// filename: src/auth/auth.routes.ts
import { Router, Request, Response } from 'express';
import {
  AUTHORIZE_ENDPOINT,
  generateCodeVerifier,
  generateCodeChallenge,
} from './azure-config';
import { exchangeCodeForTokens } from './auth.service';

export const authRouter = Router();

const COOKIE_OPTIONS = {
  httpOnly: true,
  sameSite: 'lax' as const,
};

const PKCE_COOKIE_OPTIONS = {
  ...COOKIE_OPTIONS,
  maxAge: 5 * 60 * 1000, // 5 minutes — only needed for the duration of the login
};

// Login page
authRouter.get('/login', (req: Request, res: Response) => {
  res.render('login', { title: 'Login' });
});

// Start Azure login
authRouter.get('/auth/start', (req: Request, res: Response) => {
  const codeVerifier = generateCodeVerifier();
  const codeChallenge = generateCodeChallenge(codeVerifier);

  // Temporarily store the verifier so we can use it in the callback
  res.cookie('pkce_verifier', codeVerifier, PKCE_COOKIE_OPTIONS);

  const params = new URLSearchParams({
    client_id: process.env.B2C_CLIENT_ID!,
    response_type: 'code',
    redirect_uri: process.env.B2C_REDIRECT_URI!,
    scope: process.env.B2C_SCOPES ?? '',
    code_challenge: codeChallenge,
    code_challenge_method: 'S256',
  });

  res.redirect(`${AUTHORIZE_ENDPOINT}?${params.toString()}`);
});

// Azure callback
authRouter.get('/auth/callback', async (req: Request, res: Response) => {
  const code = req.query.code as string;
  const codeVerifier = req.cookies?.pkce_verifier;

  if (!code || !codeVerifier) {
    return res.redirect('/login');
  }

  try {
    const tokens = await exchangeCodeForTokens(code, codeVerifier);

    // Set auth cookies
    res.cookie('access_jwt', tokens.access_token, COOKIE_OPTIONS);

    if (tokens.refresh_token) {
      res.cookie('refresh_jwt', tokens.refresh_token, COOKIE_OPTIONS);
    }

    // Clean up the temporary PKCE cookie
    res.clearCookie('pkce_verifier');

    res.redirect('/');
  } catch (err) {
    console.error(err);
    res.redirect('/login');
  }
});

// Logout
authRouter.get('/logout', (req: Request, res: Response) => {
  res.clearCookie('access_jwt');
  res.clearCookie('refresh_jwt');
  res.redirect('/login');
});
```

Walking through each route:

- **`/login`** simply renders a login page (a template we'll create in Step 11).
- **`/auth/start`** generates a fresh PKCE verifier/challenge pair, temporarily stores the verifier in a short-lived cookie, and builds the authorization URL by hand using `URLSearchParams` — including `code_challenge` and `code_challenge_method: "S256"` — then redirects the browser to Azure B2C's hosted login page.
- **`/auth/callback`** is where Azure B2C redirects the user back to after they log in, with an authorization `code` in the query string. We retrieve the `pkce_verifier` cookie set earlier, exchange the code and verifier for tokens, store the resulting access and refresh tokens as `httpOnly` cookies, clean up the temporary PKCE cookie, and redirect to the home page.
- **`/logout`** clears both auth cookies and sends the user back to the login page. Note this only ends the _local_ session — it doesn't sign the user out of Azure B2C itself, which would require redirecting to Azure's logout endpoint as well if a full single-sign-out is desired.

<Callout type="warning" title="Why store the verifier in a cookie?">
  The code verifier generated in `/auth/start` needs to be available again when
  `/auth/callback` runs — but these are two separate requests, possibly handled
  by different server instances if you're running multiple. A short-lived
  `httpOnly` cookie is a simple way to carry it across the redirect to Azure and
  back. In a multi-instance deployment, make sure cookies are consistent across
  instances, or use a shared store (like Redis) keyed by a `state` parameter
  instead.
</Callout>

<Callout type="tip" title="sameSite: 'lax'">
  Setting `sameSite: "lax"` on these cookies helps protect against CSRF attacks
  by preventing the cookies from being sent on most cross-site requests, while
  still allowing them to be sent when the user navigates to your site directly
  (e.g., via the Azure B2C redirect).
</Callout>

## Step 9: Create the auth middleware

This is where the backend actually _enforces_ authentication. The middleware runs on every request and decides whether to let it through, refresh the tokens, or redirect to login.

Create `src/auth/auth.middleware.ts`:

```ts
// filename: src/auth/auth.middleware.ts
import { Request, Response, NextFunction } from 'express';
import {
  isExpired,
  clearAuthCookies,
  refreshAccessToken,
} from './auth.service';

const COOKIE_OPTIONS = {
  httpOnly: true,
  sameSite: 'lax' as const,
};

export async function authMiddleware(
  req: Request,
  res: Response,
  next: NextFunction,
) {
  // Skip auth routes
  if (
    req.path.startsWith('/login') ||
    req.path.startsWith('/auth') ||
    req.path.startsWith('/static')
  ) {
    return next();
  }

  const accessToken = req.cookies?.access_jwt;
  const refreshToken = req.cookies?.refresh_jwt;

  // No access token
  if (!accessToken) {
    return res.redirect('/login');
  }

  // Access valid
  if (!isExpired(accessToken)) {
    return next();
  }

  // No refresh token
  if (!refreshToken) {
    clearAuthCookies(res);
    return res.redirect('/login');
  }

  // Refresh expired
  if (isExpired(refreshToken)) {
    clearAuthCookies(res);
    return res.redirect('/login');
  }

  // Attempt refresh
  try {
    const tokens = await refreshAccessToken(refreshToken);

    res.cookie('access_jwt', tokens.access_token, COOKIE_OPTIONS);

    if (tokens.refresh_token) {
      res.cookie('refresh_jwt', tokens.refresh_token, COOKIE_OPTIONS);
    }

    return next();
  } catch {
    clearAuthCookies(res);
    return res.redirect('/login');
  }
}
```

This logic follows a clear decision tree on every request:

1. **Is this an auth-related or static route?** If so, skip the checks entirely — we don't want to redirect `/login` to `/login` in an infinite loop.
2. **Is there an access token at all?** No token means no session — redirect to login.
3. **Is the access token still valid?** If yes, we're done — call `next()` and let the request proceed.
4. **Is there a refresh token?** If the access token expired and there's no refresh token, the session can't be recovered — clear cookies and redirect to login.
5. **Is the refresh token also expired?** If so, the session is fully dead — same outcome.
6. **Attempt the refresh.** If everything checks out, call Azure's token endpoint with `grant_type: refresh_token` to get a new access token (and possibly a new refresh token), set the new cookies, and proceed. If the refresh call itself fails (e.g., Azure rejects it), clear cookies and redirect to login.

The result is that **every authenticated route automatically handles token refresh transparently** — by the time a request reaches your actual page handlers, you can simply assume the user is authenticated with a valid access token.

## Step 10: Wire it into the app

In your main app file, register the cookie parser, mount the auth routes, and apply the middleware globally:

```ts
// filename: index.ts
import express from 'express';
import cookieParser from 'cookie-parser';
import { authRouter } from './auth/auth.routes';
import { authMiddleware } from './auth/auth.middleware';

const app = express();

app.use(cookieParser());
app.use(authRouter);
app.use(authMiddleware);

// ...your other routes go here, all protected by authMiddleware

app.listen(3000);
```

Order matters here: the auth routes are mounted _before_ the middleware, so requests to `/login`, `/auth/start`, etc. are handled directly. The middleware's own path checks are still useful as a safeguard, but mounting order keeps things explicit. Every route registered after `app.use(authMiddleware)` is automatically protected — no need to remember to add auth checks to each one individually.

## Step 11: Create the login page

Finally, create a minimal login view, e.g. `views/login.ejs` if you're using EJS as your templating engine:

```html
<!-- filename: views/login.ejs -->
<!DOCTYPE html>
<html>
  <head>
    <title>Login</title>
  </head>

  <body>
    <h1>Sign In</h1>
    <a href="/auth/start">Sign In With Azure B2C</a>
  </body>
</html>
```

This is intentionally bare — its only job is to give the user a link that kicks off the `/auth/start` route, which redirects to Azure B2C's hosted login page. From there, Azure handles the actual sign-in UI.

## What changes for existing frontend code

With this architecture in place, authentication decisions are made **before** a page is ever rendered — the middleware either lets the request through or redirects to `/login`. This has a direct impact on existing frontend authentication code:

- It's no longer responsible for _deciding_ whether the user is authenticated — by the time any client-side code runs, the server has already guaranteed it.
- It's no longer responsible for managing tokens, refresh logic, or redirects on auth failure.
- What remains is purely **UI state**: displaying the user's name, showing/hiding UI elements based on role, and so on — using data the server can pass into the rendered view.

In many cases, this means existing frontend auth modules can be significantly simplified, with large chunks of token-management code removed entirely.

<Callout type="info" title="Why this is the right direction">
  Resolving authentication on the server, before rendering, is exactly what
  makes SSR predictable: a page either renders because the user is
  authenticated, or the user never sees it because they were redirected. There's
  no in-between "loading auth state" flash that frontend-driven auth often
  introduces.
</Callout>

## Direct API calls vs. the MSAL SDK

It's worth being clear about the trade-offs of this approach compared to using Microsoft's `@azure/msal-node` SDK:

|               | Direct API calls                               | MSAL SDK                              |
| ------------- | ---------------------------------------------- | ------------------------------------- |
| Dependencies  | None beyond `crypto`/`fetch` (built into Node) | Adds `@azure/msal-node`               |
| PKCE          | Implemented manually (as shown above)          | Handled internally                    |
| Token caching | You manage it (here, via cookies)              | Has its own in-memory/cache providers |
| Visibility    | Full control over every request/response       | Some details abstracted away          |
| Portability   | Easy to port to any language                   | Tied to available SDK languages       |

Neither approach is "more correct" — the direct API approach is a good fit if you want minimal dependencies, full transparency into the OAuth flow, or need to implement the same logic in a language without an MSAL SDK. The MSAL SDK is a good fit if you'd rather not maintain the PKCE and token-exchange code yourself and are working in a language it supports well.

## Summary

| Piece                | Role                                                             |
| -------------------- | ---------------------------------------------------------------- |
| `azure-config.ts`    | Azure endpoint URLs and PKCE verifier/challenge generation       |
| `auth.service.ts`    | Token exchange, refresh, expiry checks, cookie clearing          |
| `auth.routes.ts`     | Login page, `/auth/start`, `/auth/callback`, `/logout` routes    |
| `auth.middleware.ts` | Validates/refreshes tokens on every request, redirects if needed |
| `login.ejs`          | Minimal page linking to `/auth/start`                            |

<Callout type="info" title="Bottom line">
  By moving token issuance, validation, and refresh entirely to the backend —
  and talking to Azure B2C's OAuth endpoints directly — tokens never touch
  client-side JavaScript, authentication is resolved before any page renders,
  and you get full visibility into exactly how the OAuth 2.0 + PKCE flow works
  under the hood.
</Callout>
