Every year someone writes "you don't need Tailwind/styled-components/CSS Modules, just write CSS." And every year the counter-arguments are the same: specificity wars, global scope, no co-location.

Those arguments are weaker in 2024 than they've ever been.

## What Modern CSS Gives You

**Nesting** — without a preprocessor:

```css
/* filename: card.css */
.card {
  padding: 1.5rem;
  border-radius: 12px;

  &:hover {
    border-color: var(--accent-500);
  }

  & .card-title {
    font-size: 1.25rem;
  }
}
```

**Custom properties with fallbacks:**

```css
/* filename: theme.css */
:root {
  --color-surface: #fff;
  --color-text: #111;
}

.dark {
  --color-surface: #0e0e0c;
  --color-text: #f0efe9;
}

.component {
  background: var(--color-surface, #fff);
  color: var(--color-text, #111);
}
```

**Cascade layers** — a proper solution to specificity:

```css
/* filename: styles.css */
@layer base, components, utilities;

@layer base {
  h1 { font-size: 2rem; }
}

@layer utilities {
  .text-lg { font-size: 1.125rem; }
}
/* utilities always wins over base, regardless of source order */
```

## Where the Argument Falls Apart

I'm not saying you should abandon what's working. If your team is fluent in Tailwind and shipping fast, don't change a thing.

The argument is narrower: **stop treating plain CSS as a legacy choice**. It's a first-class tool that ships zero runtime overhead, works in every environment, and now has the features that used to require build tools.

## The Tradeoffs That Still Exist

Plain CSS still lacks:
- **True component scoping** without a build step (CSS Modules solve this)
- **Co-located styles** (always a file jump away)
- **Dynamic styles** based on JS state without custom properties

If those matter, Tailwind or CSS-in-JS is still the better tool. But if you're writing a landing page, a documentation site, or anything without heavy dynamic UI, plain CSS in 2024 is genuinely good enough.

Know your tools. Use the right one for the job.
