TypeScript's type system is huge. Most of it you won't need. These are the patterns I find myself enforcing in every code review because they prevent the most common bugs on multi-person teams.

## 1. Prefer Discriminated Unions Over Boolean Flags

Boolean flags multiply: `isLoading`, `isError`, `isEmpty`, `isSuccess` — four booleans that create 16 possible states, most of which are invalid.

Use a discriminated union instead:

```ts
// filename: types/async-state.ts
type AsyncState<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: T }
  | { status: 'error';   error: string };
```

Now TypeScript narrows the type for you in switch statements, and invalid states are unrepresentable.

## 2. Use `satisfies` Instead of Type Assertions

`as SomeType` is a lie. It tells the compiler "trust me" and suppresses errors. `satisfies` validates the shape without widening the type:

```ts
// filename: config/routes.ts
// BAD: 'as' hides errors
const config = { path: '/dashboard', icon: 'home' } as RouteConfig;

// GOOD: 'satisfies' catches errors AND keeps the narrower literal type
const config = { path: '/dashboard', icon: 'home' } satisfies RouteConfig;
```

## 3. Exhaustive Checks in Switch Statements

When you add a new variant to a union, make sure every switch statement handles it:

```ts
// filename: utils/format.ts
function formatStatus(status: 'active' | 'inactive' | 'pending'): string {
  switch (status) {
    case 'active':   return 'Active';
    case 'inactive': return 'Inactive';
    case 'pending':  return 'Pending';
    default: {
      const _never: never = status; // Compile error if a case is missing
      return _never;
    }
  }
}
```

## 4. Avoid `any`, Reach for `unknown`

`any` disables type checking entirely. `unknown` forces you to narrow before use:

```ts
// filename: utils/parse.ts
function parseJson(raw: string): unknown {
  return JSON.parse(raw);
}

const result = parseJson('{"name":"test"}');
// Must check before using — TypeScript enforces this
if (typeof result === 'object' && result !== null && 'name' in result) {
  console.log(result.name);
}
```

## 5. Type Your API Responses at the Boundary

Don't `any` your fetch calls. Use a validation library like `zod` at the network boundary and let types flow inward:

```ts
// filename: lib/api.ts
import { z } from 'zod';

const UserSchema = z.object({ id: z.string(), name: z.string() });
type User = z.infer<typeof UserSchema>;

async function getUser(id: string): Promise<User> {
  const res  = await fetch(`/api/users/${id}`);
  const data = await res.json();
  return UserSchema.parse(data); // throws if shape is wrong
}
```

These five patterns alone eliminate most of the "it works in TS but breaks at runtime" bugs I've seen on large teams.
